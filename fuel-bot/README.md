# fuel-bot — Telegram-бот выдачи топлива

Микросервис поверх той же предметной области, что и приложение для водителей АТЗ:
смена, выдача топлива, приёмка, остаток в цистерне — но в интерфейсе Telegram.

Работает автономно: своя база SQLite с демо-данными, никаких обращений к боевому серверу.

---

## Быстрый старт

```bash
# 1. Создать бота: в Telegram написать @BotFather → /newbot → получить токен
cp .env.example .env      # вставить токен в BOT_TOKEN

# 2. Установить зависимости и запустить
npm install
npm start                 # или npm run dev — с автоперезапуском

# 3. В Telegram открыть своего бота → /start → PIN 1234
```

Проверка без запуска бота:

```bash
npm run lint    # проверка типов
npm test        # 12 тестов доменной логики
```

**Демо-доступы:** PIN `1234` (Иванов И.И.) и `5678` (Петров П.П.).
В базе два АТЗ, три организации и восемь единиц техники.

### Если не запускается

**`Error: file is not a database`** — `DB_PATH` в `.env` указывает не на базу.
Частый случай: автодополнение в редакторе подставляет путь к исходнику
(`src/db.ts`) вместо файла базы. Должно быть:

```
DB_PATH=./fuel-bot.db
```

Строку вообще можно удалить — тогда возьмётся значение по умолчанию.
С версии с проверкой пути бот в этом случае объясняет причину сам.

**`Не задан BOT_TOKEN`** — нет файла `.env` или в нём нет токена.
Пробелы вокруг `=` допустимы, Node их обрезает.

**База повреждена** — удалить `fuel-bot.db`, он создастся заново с демо-данными.

## Как это устроено

### Главная сложность — Telegram не помнит контекст

Каждое сообщение приходит боту само по себе. Бот не знает, что пользователь
«сейчас вводит литры» — если только не хранит это сам.

Поэтому в основе — **конечный автомат** (`src/session.ts`): для каждого
пользователя хранится шаг, на котором он находится. Одно и то же «120»
означает разное в зависимости от шага:

| Шаг | Что значит «120» |
|-----|------------------|
| `await_opening_liters` | остаток в цистерне на старте смены |
| `await_dispense_liters` | сколько литров выдаём |
| `await_receipt_liters` | сколько литров принимаем |
| `idle` | ничего, бот предложит нажать кнопку |

### Два источника ввода

Telegram доставляет действия пользователя двумя разными способами, и им
соответствуют два обработчика:

| Что делает пользователь | Что приходит боту | Обработчик |
|---|---|---|
| Нажимает inline-кнопку | `callback_query` с полем `data` | `handlers/callbacks.ts` |
| Пишет текст | `message:text` | `handlers/text.ts` |

Кнопки задают **навигацию** (куда идём), текст даёт **данные** (что вводим).

### Формат callback_data

Кнопки несут строку вида `действие:подкоманда:аргумент`:

```
shift:start           → начать смену
shift:atz:<uuid>      → выбран конкретный АТЗ
dispense:veh:<uuid>   → выбрано ТС для выдачи
dispense:save         → подтвердить и записать
nav:menu              → вернуться в меню
```

Telegram ограничивает `callback_data` **64 байтами**, поэтому в кнопке едет
только идентификатор. Всё остальное (объём, ФИО получателя) лежит в шаге сессии —
см. `confirm_dispense` в `session.ts`.

## Структура

```
src/
├── index.ts              точка входа: команды, регистрация обработчиков, запуск
├── db.ts                 схема SQLite, запросы, демо-данные
├── domain.ts             бизнес-правила: валидация, остаток, операции смены
├── domain.test.ts        12 тестов — без Telegram, только правила
├── session.ts            конечный автомат: шаги диалога
├── keyboards.ts          inline-клавиатуры и формат callback_data
├── views.ts              тексты сообщений и сборка меню
└── handlers/
    ├── callbacks.ts      нажатия кнопок → ветвление по действию
    └── text.ts           текст → ветвление по текущему шагу
```

Ключевое разделение: **`domain.ts` ничего не знает про Telegram**. Решения
принимаются там, а хендлеры только ведут диалог. Поэтому правила проверяются
обычными тестами, а бот при желании переносится на другой интерфейс без
переписывания логики.

## Сценарий выдачи топлива

```
[⛽ Выдать топливо]              callback  dispense:begin
        ↓                        шаг → await_vehicle_query
ввод «Е701»                      текст
        ↓                        поиск по части госномера
[Е701КХ72 · КамАЗ 6520]          callback  dispense:veh:<id>
        ↓                        шаг → await_dispense_liters
ввод «250.5»                     текст
        ↓                        проверка: хватает ли в цистерне
ввод «Петров П.П.»               текст
        ↓                        шаг → confirm_dispense
[✅ Записать] [✖️ Отмена]        callback  dispense:save
        ↓
запись + пересчёт остатка → меню
```

Ветвления на каждом шаге: неверный формат числа, объём больше остатка,
ничего не найдено по запросу, смену закрыли пока водитель вводил данные.

## Правила предметной области

Всё в `domain.ts`, всё покрыто тестами:

- **Объём** — больше нуля, не более `99999.99`, максимум два знака после запятой.
  Принимается и точка, и запятая: водитель пишет как удобно.
- **Выдать больше, чем есть в цистерне, нельзя.** Проверка делается дважды:
  сразу после ввода объёма (чтобы не заставлять вводить ФИО зря) и перед самой записью.
- **Одна открытая смена на один АТЗ.** Гарантируется и проверкой в коде — чтобы
  выдать понятную ошибку, — и уникальным индексом в базе, на случай гонки.
- **Остаток не хранится, а вычисляется:** `остаток на старте − выдачи + приёмки`.
  Единственный источник правды — события, а не счётчик, который можно рассинхронизировать.

### Про один пойманный баг

Первая версия `closeShift()` проверяла статус смены по объекту, переданному
в функцию. Тест это поймал: объект в памяти продолжал считать себя открытым
после закрытия в базе, и повторный вызов закрывал смену второй раз, ещё раз
перезаписывая остаток в АТЗ.

Правильно — перечитывать состояние из базы. То же исправлено в `dispense()`
и `receive()`: смену могли закрыть, пока водитель вводил данные.

Это ровно тот класс ошибок, который в приложении для планшетов проявился как
двойное нажатие, создававшее две параллельные смены: **состояние в памяти
устаревает, решения нужно принимать по источнику правды**.

## Чего здесь нет

Осознанно вынесено за рамки демо:

- **Офлайн-режим** — в Telegram он невозможен: без сети сообщение просто не уйдёт.
  В приложении на планшете это ключевая часть, здесь — нет.
- **Фото ТТН при приёмке** — Telegram умеет принимать фото, но очередь загрузки
  с повторами повторяет то, что уже сделано в основном приложении.
- **Хранение сессий в базе** — состояние живёт в памяти процесса. Для демо
  достаточно; для боевого бота меняется только хранилище, логика шагов та же.

## Развёртывание

Бот живёт на сервере в Хельсинки (Aeza, `109.120.185.57`) под pm2.

**Важно: с российского хостинга бот работать не будет** — `api.telegram.org`
оттуда недоступен ни по IPv4, ни по IPv6, хотя остальной интернет открыт.
Проверено на VPS reg.ru: обычный HTTPS проходит, Telegram — нет.

Обновление после правок:

```bash
rsync -az --delete --exclude node_modules --exclude '.env*' --exclude '*.db' \
  ./src ./package.json ./tsconfig.json ./ecosystem.config.cjs \
  root@109.120.185.57:/opt/fuel-bot/

ssh root@109.120.185.57 'cd /opt/fuel-bot && npm install --omit=dev && pm2 restart fuel-bot'
```

Полезное на сервере:

```bash
pm2 list                      # статус
pm2 logs fuel-bot             # логи в реальном времени
pm2 restart fuel-bot          # перезапуск
```

Автозапуск после перезагрузки включён (`pm2 startup` + `pm2 save`).

> **Про токен в логах.** При сетевой ошибке grammY пишет полный URL запроса,
> а в нём есть токен. Логи лежат в `/var/log/fuel-bot.*.log` с доступом только
> для root, но если лог куда-то копируется — токен надо считать раскрытым
> и перевыпускать через `/revoke` у @BotFather.

## Стек

Node.js 22+ · TypeScript · [grammY](https://grammy.dev) · `node:sqlite`

Единственная внешняя зависимость — grammY. База берётся из встроенного в Node
модуля `node:sqlite`, поэтому нативных зависимостей и сборки нет вообще.
